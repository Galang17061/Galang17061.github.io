01Overview

What Strata is

Strata is a reliability analysis platform built around the reliability block diagram method. An engineer models a system as a tree of subsystems and components, wires the blocks in series, parallel or k-out-of-n, records every failure a component has had, and Strata works out, from the components upward, how likely each block and the whole system is to still be working after a given number of running hours.

I built both halves: the Go API that does the mathematics and the Next.js app engineers work in, plus the Docker and Google Cloud setup the demo runs on. The launcher at the bottom of this page boots a real instance when you ask for it.

02Problem

Reliability work still lives in spreadsheets

Failure records are scattered, distribution fitting is done by hand, and the reliability of a whole system depends on how its blocks are wired, which a spreadsheet cannot express. The tools that can are desktop-bound and expensive.

  • Every failure a component has had must be logged in one place before a fit means anything.
  • Series, parallel and k-out-of-n blocks compose differently, so the system formula has to follow the drawing.
  • Choosing a vendor for each slot under a budget means re-running every calculation for every combination.

03What I built

Five parts, one system

Reliability analytics

Weibull, exponential and Poisson models are fitted to each component's failure log. Blocks are wired in series, parallel or k-out-of-n; Strata derives an algebraic reliability formula from the drawn topology and evaluates it from the components upward, at any number of running hours. Every system keeps versioned snapshots, the last twenty taken automatically, so a change can be compared with what came before.

R2oo3(t) = 3R(t)2 − 2R(t)3 · Rseries = ∏ Ri · Rparallel = 1 − ∏ (1 − Ri) · RWeibull(t) = e−(t/η)β

Genetic-algorithm optimisation studio

Each component slot has a set of candidate vendors, each with its own failure rate and unit cost. The studio runs a genetic algorithm over those choices with roulette-wheel selection, single-point crossover, elitism and an early stop after 25 stalled generations. Three modes: maximise reliability, maximise reliability within a budget, or trade cost against a reliability floor.

Searches are heavy, so a semaphore in the API caps how many run at once, two by default with a short queue wait. When the studio is full the caller is told so instead of the whole service slowing down.

Backend and data

A Go API on chi and sqlx, backed by SQL Server 2022 and shipped as a single static binary. Reliability arithmetic uses decimals rather than floats. JWT sign-in with per-module rights, an audit trail of requests, Excel import of master data, and a generated OpenAPI spec served with Swagger UI. The process exposes its own Prometheus metrics.

Frontend

Next.js 15 with React 19, exported as a static site and served by nginx. The workspace has a React Flow canvas for wiring blocks, a component sheet with the failure log and its fit, Recharts plots with PNG and SVG export, and the system formula rendered with KaTeX. Tailwind 4 and shadcn/ui underneath, with a guided tour for first-time users.

Operations

Nine Compose services: database, API, web, a twin test database for load runs, Mailpit, Uptime Kuma, Prometheus, Grafana and a k6 runner. Caddy terminates TLS in front of it on a Google Cloud VM that a small wake service starts on demand and shuts down after thirty idle minutes.

04Architecture

How the pieces connect

A browser talks to Caddy, which terminates TLS and routes to the static Next.js build served by nginx and to the Go API. The API does all reliability computation and persists to SQL Server. Prometheus scrapes the API every fifteen seconds and Grafana reads from it. All of it runs as containers on one Google Cloud VM that the demo launcher can start on request.
